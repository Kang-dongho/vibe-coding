1어느 파일

a는 전, b는 후. 파일 이름부터 봅니다 — 요청과 관계있는 파일인가?

2어디쯤

12번째 줄 근처, draw_trend 함수 안. 위치를 알면 범위를 판단할 수 있습니다.

34 무엇이

SIZE · 먼저 크기를 본다

요청 크기와 변경 크기가 맞는지부터 봅니다

$ git diff --stat
 chart.py           |  2 +-
 stats.py           |  6 ++----
 requirements.txt   |  1 +
 3 files changed, 4 insertions(+), 5 deletions(-)

"차트 글자 키우기"에 파일 3개 — 두 개는 설명이 필요합니다.

보이는 것해석
요청 1개, 파일 1~2개보통. 다섯 질문으로 빠르게
요청 1개, 파일 5개+범위가 넘쳤을 가능성. 이유부터 묻기
수백 줄 변경나눠 달라고 요청 — 한 번에 판단 불가
지운 줄 ≫ 추가한 줄무엇을 지웠는지 반드시 확인
git diff --stat 한 줄이면 내용을 보기 전에 규모를 압니다. 이것만으로 사고의 절반을 걸러 냅니다. "나눠 달라"는 정당한 요청입니다. 사람 개발자 사이에서도 수백 줄짜리 변경은 리뷰가 제대로 안 된다는 게 상식입니다.
CHECKLIST · 다섯 질문

하나라도 "모르겠다"면, 승인하지 않고 묻습니다

  • 1범위 — 요청한 것만 바뀌었나? 요청에 없던 파일 · 기능이 있나?diff --stat
  • 2삭제 — 지운 줄은 무엇이고, 왜 지웠나? 검사 · 필터 · 예외 처리가 사라졌나?빨간 줄
  • 3비밀 — 비밀번호 · 키 · 서버 주소 · 개인 경로가 새로 들어갔나?초록 줄
  • 4증거 — 실행 결과 · 테스트 · 전후 비교를 봤나? "됐어요"는 증거가 아님실행
  • 5되돌리기 — 문제가 생기면 어떻게 돌아가나? 커밋이 따로 있나?git

다섯 질문은 코드 실력이 아니라 주의력으로 답할 수 있게 고른 것입니다.

클릭할 때마다 하나씩. 이 덱의 중심 장입니다. 인쇄해서 모니터 옆에 붙여 두라고 권합니다. 2번과 3번은 diff의 색으로 바로 찾을 수 있습니다. 삭제는 빨간 줄, 비밀은 초록 줄에서 나옵니다.

계정 · 비밀번호 · 서버 주소. 커밋되면 기록에 영원히 남습니다.

EXPLAIN · 만든 AI에게 설명시키기

"무엇을 바꿨나"보다 "무엇이 달라지나"를 묻습니다

💬 설명 요청 템플릿
방금 변경을 비개발자에게 설명해줘.
1) 사용자 입장에서 달라지는 것 (3줄)
2) 바뀐 파일마다: 왜 바꿨나 / 요청과의 관계
3) 요청에 없던 변경 — 없으면 "없음"이라고
4) 지운 코드 전부와 지운 이유
5) 이 변경으로 틀어질 수 있는 숫자나 화면
6) 확인 방법: 내가 직접 해 볼 수 있는 것 하나

"없음"이라고 쓰게 하기

3번을 비워 두지 못하게 하면, AI가 슬쩍 넣은 변경을 스스로 털어놓습니다.

설명과 diff를 맞춰 보기

설명에 없는 파일이 diff에 있다면, 그게 가장 먼저 볼 곳입니다.

6번은 직접

"이 화면에서 EQ-03을 고르면 평균이 4005.5로 나와야 함" — 1분 확인이 가장 강한 증거입니다.

만든 AI의 설명은 유용하지만 완전히 믿을 수는 없습니다. 그래서 설명과 diff를 대조하는 게 핵심입니다. 6번 "내가 직접 해 볼 수 있는 것"은 검증 덱의 "증거를 받는다"와 같은 원칙입니다.
SECOND EYES · 독립 리뷰어

만든 AI는 자기 답에 후합니다 — 과정을 모르는 눈을 하나 더

💬 새 세션(또는 리뷰 전용 에이전트)에게
너는 리뷰어야. 아래 요청과 diff만 보고 판단해줘.
[요청] 두께 추이 차트 제목 글자 키우기
[diff] (git diff 전체 붙여 넣기)

판정: 승인 / 수정 요청 중 하나.
수정 요청이면 줄 위치와 이유를 표로.
특히 범위 밖 변경, 지운 검사, 비밀값,
예외 숨김, 테스트 변경을 확인해줘.

새 세션이 핵심

만든 대화의 맥락이 없어야 "왜 그렇게 했는지"에 설득당하지 않습니다.

요청을 꼭 함께

diff만 주면 "좋은 코드인가"를 보고, 요청을 주면 "요청대로인가"를 봅니다.

최종 판단은 사람

리뷰어 AI도 틀립니다. 두 의견이 다르면 그 지점을 직접 봅니다.

하네스 덱의 ⑥ 분업 칸을 리뷰에 적용한 장입니다. 리뷰 전용 서브에이전트를 만들어 두면 매번 프롬프트를 쓰지 않아도 됩니다(orchestration 덱). diff에 비밀값이 섞여 있을 수 있으니, 외부 도구에 붙일 때는 보안 약속을 지킵니다.

SAFETY NET · 승인 뒤에 문제를 찾았다면

변경마다 커밋이 따로 있으면, 한 줄로 되돌립니다

$ git log --oneline
a3f9c21 feat: 차트 제목 크기 12 → 16
7b2e004 refactor: 평균 계산 함수로 합침
19d8e55 fix: 헤더 3줄 건너뛰기

$ git revert a3f9c21    # 그 커밋만 거꾸로 적용

revert는 기록을 지우지 않습니다

"되돌림"이라는 새 커밋이 생깁니다. 무슨 일이 있었는지 남습니다.

그래서 커밋은 작게

차트 · 계산 · 패키지가 한 커밋에 섞이면 차트만 되돌릴 수 없습니다.

핵심 모드에서는 접히는 심화 장입니다. 다섯 질문 중 5번(되돌리기)의 실제 방법입니다. 커밋 해시는 예시입니다.
🖐 실습 · 문제가 숨은 diff 리뷰하기 (15분)

AI가 일부러 문제를 숨긴 diff에서 다섯 질문으로 찾아냅니다

배우는 것 — 코드를 다 읽지 않고, 다섯 질문과 빨간 깃발로 판정하는 법.

💬 에이전트에게 이렇게 말하세요
리뷰 연습을 하고 싶어. 짧은 파이썬 프로젝트와
"차트 제목 바꾸기" 요청에 대한 diff를 만들어줘.
diff 안에 문제를 3개 숨겨줘 (범위 밖 변경, 삭제된 검사,
비밀값·예외 숨김·테스트 끄기 중에서).
정답은 알려주지 말고, 내가 찾은 걸 말하면 채점해줘.

✅ 완료 기준

  • diff --stat으로 크기부터 봤다
  • 숨은 문제 3개 중 2개 이상을 찾았다
  • 각 문제에 반려 문장(위치 · 이유 · 원하는 상태)을 썼다

🧯 막히면

빨간 줄만 먼저 전부 읽으세요. 그다음 초록 줄에서 따옴표 안의 값(비밀번호, 주소, 경로)만 훑어봅니다. 그것만으로 대부분 찾습니다.

15분. AI를 출제자로 쓰는 실습입니다. 두 번 정도 반복하면 다섯 질문이 손에 붙습니다. 세 번째 완료 기준이 "찾기"에서 "고치게 하기"로 이어지는 연습입니다.
정리

오늘 가져갈 습관 세 가지

1. 크기부터, 빨강과 초록만

diff --stat으로 규모, 빨간 줄은 지운 것, 초록 줄은 새로 생긴 것.

2. 다섯 질문 — 범위 · 삭제 · 비밀 · 증거 · 되돌리기

하나라도 "모르겠다"면 승인하지 않고 묻습니다.

3. 설명은 만든 AI에게, 판정은 독립된 눈과 사람이

"요청에 없던 변경: 없음"까지 쓰게 하고, 새 세션 리뷰어와 대조합니다.

세 습관으로 마무리하고 Q&A. 다섯 질문 장을 인쇄해 나눠 주면 좋습니다.
