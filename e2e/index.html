결론부터 — 이 세 줄이면 됩니다

E2E 테스트는 사람이 하던 "열어서 눌러 보기"를 로봇에게 맡기는 일입니다. 부품이 아니라 완성품을 검사합니다.

  1. 1
    E2E = 화면에서 DB까지, 사용자가 가는 길을 통째로부품 검사(단위 테스트)가 다 통과해도 완성품은 안 돌 수 있습니다.
  2. 2
    많이 말고, 핵심 길 3~5개만느리고 잘 깨지니 "이게 안 되면 큰일"인 시나리오만 고릅니다.
  3. 3
    AI의 완료 기준을 "E2E 통과 + 스크린샷"으로"다 됐어요" 대신 증거를 받습니다. sleep 대신 expect로 기다립니다.

속은 몰라도 된다

대신 느리다

브라우저를 실제로 띄우니 한 개에 수 초. 그래서 골라서 씁니다.

노란 점이 테스트 한 번이 지나가는 길입니다. 단위 테스트는 이 중 한 칸만 봅니다. 두 번째 카드가 바이브 코딩에 특히 좋습니다. AI가 내부를 크게 고쳐도, 사용자 흐름 테스트는 그대로 둔 채 "이게 여전히 통과하나"만 보면 됩니다.

"이게 안 되면 큰일"인 길부터 — 사내 대시보드 예시

  • 1첫 화면이 열린다 — 에러 없이 제목과 오늘 날짜가 보인다가장 먼저
  • 2고르면 바뀐다 — 설비 EQ-03 선택 → 조회 → 차트 제목이 EQ-03핵심 흐름
  • 3받은 파일이 맞다 — CSV 다운로드 → 행 수가 화면의 건수와 같다데이터가 나감
  • 4잘못 넣으면 막는다 — 시작일 > 종료일 → 빨간 안내 문구, 조회 안 됨예외 하나
  • ✕버튼 색 · 글꼴 · 간격 — E2E로 잡지 않는다눈으로

고르는 기준: 매일 쓰는 길 · 데이터가 밖으로 나가는 길 · 한 번 터져서 혼난 길.

클릭할 때마다 하나씩. 4번은 AI가 잘 빠뜨리는 "예외 길"입니다 — 해피 패스만 만들어 주기 때문에. 디자인은 E2E 대상이 아닙니다. 픽셀까지 비교하는 테스트(스크린샷 비교)도 있지만, 입문 단계에서는 깨지기만 하고 얻는 게 적습니다.

from playwright.sync_api import Page, expect

def test_설비를_고르면_차트가_바뀐다(page: Page):

    page.get_by_label("설비").select_option("EQ-03") # ② 고르기

    expect(page.get_by_text("EQ-03 평균 두께")).to_be_visible()  # ④ 확인

② LOCATOR · 버튼을 어떻게 찾나

"세 번째 div"가 아니라 사람이 부르는 이름으로 찾습니다

# ❌ 화면 구조에 묶임 — 디자인만 바꿔도 깨짐
page.locator("#root > div:nth-child(3) > button").click()
# ✅ 사람이 보는 이름 — 위치가 바뀌어도 그대로
page.get_by_role("button", name="조회").click()
page.get_by_label("시작일").fill("2026-11-17")
page.get_by_text("다운로드 완료")

이름으로 못 찾는 화면이라면, 그 화면은 스크린 리더 사용자에게도 안 보이는 화면입니다.

순서찾는 법언제
1get_by_role버튼 · 링크 · 체크박스 — 역할 + 이름
2get_by_label이름표가 붙은 입력칸
3get_by_text화면에 보이는 글자
4get_by_test_id이름이 자주 바뀌면 data-testid를 달아 둠
✕CSS 경로 · 순번마지막 수단
AI가 테스트를 짜면 가끔 CSS 경로를 씁니다. "get_by_role 우선으로"라고 한 줄 붙이면 대부분 고쳐집니다. 접근성(UI/UX 덱의 aria-label)과 연결됩니다. 아이콘 버튼에 이름을 달면 테스트도 쉬워집니다.

⚠️ TRAP · sleep으로 기다리면

3. AI에게 다듬기

코드를 몰라도 시나리오는 우리가 제일 잘 압니다. 녹화는 그 시나리오를 코드로 옮겨 주는 통역사입니다. 녹화 결과는 지저분할 수 있습니다(불필요한 클릭, 위치 기반 선택자). 그래서 3번 — AI에게 다듬기를 붙입니다.

통과할 때는 아무것도 안 남기고, 실패할 때만 남기는 설정입니다. 저장 공간도 아끼고, 증거도 남습니다. 이 스크린샷을 그대로 AI에게 붙여 주면 "날짜를 안 고르면 버튼이 비활성"이라는 원인을 바로 짚습니다. 영상이 필요하면 --video retain-on-failure.

"통과시키려고 테스트를 고치지 마"를 규칙에. 채점지를 고치면 의미가 없습니다.

AI가 직접 눌러 보기

Playwright MCP를 연결하면 AI가 브라우저를 직접 열어 확인합니다 → 다음 덱.

하네스 덱의 "검증 칸"을 E2E로 채우는 장면입니다. 완료 기준을 테스트로 주면, AI는 실패를 보고 스스로 고칩니다. 두 번째 카드가 중요합니다. 테스트 파일은 하네스의 deny 또는 ask 칸에 넣어 둘 수 있습니다.

❌ 테스트끼리 순서 의존

❌ 오늘 날짜에 의존

"오늘 측정값 3건"은 내일 0건이 됩니다.

INTRANET · 사내망에서 돌리기

브라우저 다운로드가 막혀도, PC에 있는 Chrome으로 됩니다

# 외부망이면 보통 이렇게 (사내망에선 막힐 수 있음)
pip install pytest-playwright
playwright install chromium

# 사내망: 설치된 Chrome / Edge를 그대로 사용
pytest tests/e2e --browser-channel chrome
pytest tests/e2e --browser-channel msedge

# 눈으로 보면서 (처음 만들 때)
pytest tests/e2e --headed --slowmo 500

패키지는 사내 저장소로

pip이 막혀 있으면 사내 PyPI 미러 주소를 쓰는 방법을 인프라 담당에게 확인합니다.

headless가 기본

평소엔 창 없이 빠르게. 처음 만들 때만 --headed로 로봇이 누르는 걸 구경합니다.

매일 아침 자동으로

배포 전 · 매일 정해진 시간에 돌리면, 고장을 사용자보다 먼저 압니다.

사내 보안 정책에 따라 다릅니다. 브라우저 바이너리 다운로드가 막혀 있다면 channel 옵션으로 설치된 Chrome·Edge를 씁니다. --slowmo 500은 동작마다 0.5초씩 쉬어서, 사람이 따라 보기 좋게 합니다. 시연할 때 좋습니다. 자동 실행은 CI/CD 덱(준비 중)에서 이어집니다.
🖐 실습 · 내 도구의 핵심 길 하나 (20분)

내 앱의 "이게 안 되면 큰일" 하나를 E2E로

배우는 것 — 시나리오를 네 동작으로 쪼개고, 이름으로 찾고, expect로 기다리고, 실패 증거를 남기는 법.

💬 에이전트에게 이렇게 말하세요
tests/e2e/에 Playwright(pytest) 테스트를 하나 만들어줘.
시나리오: (열기) → (고르기/입력) → (누르기) → (보여야 할 글자)
규칙: get_by_role · get_by_label 우선, sleep 금지,
     테스트용 데이터만 사용, 실패 시 스크린샷 · 트레이스.
먼저 --headed로 한 번 돌려 보여주고,
앱 코드를 고쳐서 통과시켜. 테스트 파일은 내가 승인할 때만 수정.

✅ 완료 기준

  • 테스트가 세 번 연속 통과한다 (가끔 실패 없음)
  • 기대 글자를 일부러 틀리게 바꾸면 실패하고 스크린샷이 남는다
  • 코드에 sleep이 없다

🧯 막히면

요소를 못 찾으면 playwright codegen으로 한 번 눌러 보고, 나온 선택자를 AI에게 붙여 주세요. 앱 서버가 먼저 켜져 있어야 합니다.

20분. "일부러 틀리게 바꿔서 실패 확인"이 핵심입니다 — 절대 실패하지 않는 테스트는 아무것도 검사하지 않는 테스트일 수 있습니다. 세 번 연속 통과는 flaky 여부를 보는 가장 싼 방법입니다.
정리

오늘 가져갈 습관 세 가지

1. 완성품은 완성품으로 검사한다

단위 테스트는 부품, E2E는 사용자가 가는 길. 판정은 화면에 보이는 것으로.

2. 적게, 이름으로, expect로

핵심 길 3~5개, 버튼은 get_by_role, 기다림은 sleep 대신 expect.

3. AI의 완료 기준으로 쓴다

"E2E 통과 + 스크린샷"을 받고, 테스트 파일은 사람이 지킵니다.
