사용자 컴퓨터에서 도는 것

프론트엔드만. 브라우저가 내려받아 실행합니다. 그래서 F12를 누르면 보입니다.

서버에서 도는 것

백엔드와 DB. 사용자는 코드를 볼 수 없고, API로 주고받는 결과만 받습니다.

노란 점이 요청입니다. 손님(사용자)은 홀(프론트)에서 메뉴를 고르고, 직원이 주문서(API)를 주방(백엔드)에 넘기고, 주방은 창고(DB)에서 재료를 꺼내 요리합니다. 주문서 양식이 정해져 있어서 홀과 주방이 서로의 일하는 방식을 몰라도 됩니다 — 이게 API의 핵심입니다.
① FRONTEND · 홀과 메뉴판

눈에 보이고 손에 닿는 건 전부 프론트입니다

ThicknessChart.jsx — React 예시

export default function ThicknessChart() {
  const [rows, setRows] = useState([]);

  useEffect(() => {                   // 화면이 뜨면
    fetch("/api/thickness?eq=EQ-03")  // API에 주문
      .then(r => r.json())
      .then(setRows);                 // 받은 걸 저장
  }, []);

  return <LineChart data={rows} />;  // 그린다
}

재료: HTML · CSS · JavaScript

뼈대 · 꾸미기 · 움직임. React, Vue는 이걸 편하게 짜는 도구입니다.

프론트가 하는 일

버튼 · 표 · 차트 그리기, 입력 받기, API에 요청하고 결과를 보여주기.

프론트에 두면 안 되는 것

비밀번호 · 키 · 권한 판단. 사용자가 F12로 전부 볼 수 있습니다.

코드를 다 읽을 필요는 없습니다. 주석만 따라가면 "화면이 뜨면 → 주문하고 → 받아서 → 그린다" 네 박자입니다. 세 번째 카드가 중요합니다. 프론트 코드는 사용자 브라우저로 내려가니까, 숨겨야 하는 것은 절대 프론트에 두지 않습니다.

② BACKEND · 주방

계산 · 규칙 · 권한은 손님이 못 보는 곳에서

main.py — FastAPI 예시

from fastapi import FastAPI
app = FastAPI()

@app.get("/api/thickness")          # 이 주소로 주문이 오면
def thickness(eq: str):
    rows = db.query(                   # 창고에서 꺼내
        "SELECT day, avg_thk FROM thk WHERE eq = ?", eq)
    return [{"day": d, "thk": round(t, 1)}   # 다듬어서
            for d, t in rows]              # 돌려준다

재료: Python · Java · Node 등

사내 도구라면 Python(FastAPI, Flask)이 흔합니다.

백엔드가 하는 일

요청 확인, 권한 검사, 계산, DB 읽고 쓰기, 결과를 정해진 모양(JSON)으로 돌려주기.

숫자가 틀리면 여기부터

평균 · 필터 · 반올림은 대부분 백엔드에서 일어납니다.

@app.get 한 줄이 "이 주소로 주문이 오면 이 함수가 처리한다"는 뜻입니다. 프론트의 fetch 주소와 같은 문자열이라는 점을 짚어 주세요 — 두 장을 이어 주는 연결선입니다. db.query는 설명을 위해 단순화했습니다. 실제로는 사용하는 DB 라이브러리에 따라 모양이 다릅니다.
③ API · 주문서

주문서 양식만 맞으면, 홀과 주방이 서로를 몰라도 됩니다

요청 (프론트 → 백엔드)

GET /api/thickness?eq=EQ-03
     ↑ 주소              ↑ 조건

응답 (백엔드 → 프론트)

200 OK
[
  { "day": "11-18", "thk": 4012.3 },
  { "day": "11-19", "thk": 3998.7 }
]

동사 넷

GET 가져오기 · POST 새로 만들기 · PUT 고치기 · DELETE 지우기

JSON = 주문서 내용

이름과 값의 묶음. 엑셀 한 행을 글자로 적은 것과 비슷합니다.

상태 코드 = 주방의 대답

200 성공 · 404 그런 주소 없음 · 500 주방에서 사고

API는 "주고받는 약속"입니다. 프론트는 주문서만 맞게 보내면 되고, 백엔드가 Python이든 Java든 상관없습니다. 상태 코드 세 개만 기억해도 디버깅이 훨씬 빨라집니다. 4로 시작하면 보낸 쪽(프론트·주소) 문제, 5로 시작하면 받는 쪽(백엔드) 문제일 가능성이 높습니다.

열마다 타입이 고정

avg_thk 칸에는 숫자만. 엑셀처럼 "측정 안 함"을 글자로 적을 수 없습니다.

SQL로 꺼냅니다

"EQ-03 행만" → 초록색 두 줄. 백엔드 코드 속 SELECT … WHERE eq = ?가 바로 이 일입니다.

여러 명이 동시에 써도 안전

엑셀 파일처럼 "누가 열어 둬서 저장 안 됨"이 없습니다.

DB는 이 덱에서는 한 장만 봅니다. SQL은 따로 덱이 있습니다. 백엔드 장의 SELECT 문과 이 표를 연결해 보여 주세요 — "WHERE eq = EQ-03"이 초록 두 줄을 꺼냅니다.

TRACE · 버튼 하나를 누르면

"EQ-03 보기"를 누른 뒤 0.3초 동안 일어나는 일

  • 1버튼 클릭을 감지하고 fetch("/api/thickness?eq=EQ-03")프론트
  • 2요청이 네트워크를 타고 서버로 — 주문서 전달API
  • 3@app.get("/api/thickness") 함수가 받아서 권한 확인백엔드
  • 4SELECT … WHERE eq = 'EQ-03'으로 두 줄을 꺼냄DB
  • 5소수 1자리로 다듬어 JSON으로 응답 (200 OK)백엔드
  • 6받은 데이터로 선 그래프를 다시 그림프론트

고장이 나면 몇 번에서 멈췄는지만 찾으면 됩니다. 그 번호가 고칠 층입니다.

클릭할 때마다 한 단계씩 나옵니다. 앞의 네 장(프론트·백엔드·API·DB)에 있던 코드 조각이 하나의 흐름으로 이어지는 장입니다. 질문: "차트가 안 그려지는데 Network 탭에 200이 찍혀 있다면, 몇 번이 의심스러울까요?" → 6번(프론트).
COMPARE · Streamlit은 왜 다르게 느껴질까

Streamlit은 네 층을 파이썬 한 파일에 접어 둔 도구입니다

app.py — Streamlit 한 파일

import streamlit as st

eq = st.selectbox("설비", ["EQ-02", "EQ-03"])  # 화면
df = pd.read_sql("SELECT …", conn,         # DB
                 params=[eq])
df["thk"] = df["thk"].round(1)               # 계산
st.line_chart(df, x="day", y="thk")          # 화면

API가 보이지 않습니다. Streamlit이 화면과 파이썬 사이를 알아서 이어 줍니다.

StreamlitFastAPI + React
파일파이썬 하나프론트 · 백엔드 따로
시작 속도⭐ 몇 분며칠
화면 자유도정해진 부품 안에서⭐ 원하는 대로

Streamlit으로 시작한 도구를 FastAPI + React로 옮기는 이유가 이 표에 있습니다. 화면을 더 자유롭게, 사용자가 늘어도 버티게, 다른 시스템이 API로 데이터를 가져가게 하려는 것입니다. 반대로 혼자 또는 소수가 쓰는 분석 도구라면 Streamlit이 훨씬 빠릅니다. 어느 쪽이 "더 좋다"가 아니라 단계의 차이입니다.
FOLDERS · 폴더로 보는 층

낯선 프로젝트를 열면, 폴더 이름으로 층부터 찾습니다

dashboard/
├─ frontend/                # ① 프론트
│  ├─ src/components/       #   화면 부품 (차트, 표)
│  ├─ src/pages/            #   화면 한 장씩
│  └─ package.json          #   npm 프로젝트 표시
├─ backend/                 # ② 백엔드
│  ├─ main.py               #   앱 시작점
│  ├─ routers/              #   ③ API 주소별 처리
│  ├─ services/             #   계산 · 규칙
│  ├─ models.py             #   ④ DB 테이블 모양
│  └─ requirements.txt      #   파이썬 패키지 목록
└─ docker-compose.yml       #   전부 한 번에 띄우기

단서 파일

package.json이 있으면 자바스크립트(대개 프론트), requirements.txt나 pyproject.toml이 있으면 파이썬.

이름은 프로젝트마다 다릅니다

client/server, web/api처럼 바뀌어도 나뉘는 방식은 같습니다.

모르겠으면 AI에게 지도부터

"폴더마다 어느 층인지 표로" — 고치기 전에 지도를 받습니다.

대표적인 모양 하나입니다. 실제 프로젝트는 이름이 다를 수 있지만, 단서 파일(package.json, requirements.txt)로 언어와 층을 거의 알아낼 수 있습니다. "고치기 전에 지도부터"는 하네스 덱의 ① 컨텍스트와 이어집니다 — 이 지도를 CLAUDE.md에 적어 두면 매번 설명하지 않아도 됩니다.
DIAGNOSIS · 증상으로 층 찾기

증상을 보면 어느 층부터 열어 볼지 정해집니다

증상먼저 볼 층확인 방법
글자가 잘리고 버튼이 겹친다① 프론트F12 → Elements에서 해당 요소 확인
버튼을 눌러도 아무 일이 없다① 프론트F12 → Console에 빨간 에러가 있나
로딩만 계속 돈다③ APIF12 → Network에서 요청이 대기 중인지, 실패했는지
404가 뜬다③ API (주소)프론트의 fetch 주소와 백엔드의 @app.get 주소 비교
500이 뜬다② 백엔드서버 터미널의 에러 메시지(Traceback)
화면은 멀쩡한데 숫자가 틀리다② 백엔드 · ④ DB같은 조건으로 DB를 직접 조회해 비교
이 표가 이 덱의 처방전입니다. 마지막 줄이 가장 위험합니다 — 에러가 안 나니까 아무도 모릅니다. 이건 검증 덱과 연결됩니다. 500 에러는 브라우저가 아니라 서버 쪽 터미널에 진짜 이유가 찍힙니다. 읽는 법은 에러 메시지 덱에서 다룹니다.

브라우저 안에 층을 들여다보는 창이 이미 있습니다

Network 탭 — 요청 목록 (예시)

Name                       Status   Type    Time

main.3f2a.js               200      script  120 ms

→ 500은 백엔드 문제. 이 줄을 눌러 Response를 보고, 서버 터미널의 에러를 AI에게 넘깁니다.

Elements

화면의 뼈대. 잘린 글자, 겹친 버튼이 어느 부품인지 찾습니다. → 프론트

Console

프론트 코드가 낸 에러. 빨간 줄을 그대로 복사해 AI에게. → 프론트

Network

주문서가 오간 기록. 상태 코드로 어느 쪽 잘못인지 갈립니다. → API

F12(맥은 Cmd+Option+I)를 직접 눌러 보게 하면 좋습니다. 사내 대시보드 아무거나 열고 Network 탭을 켠 채 새로고침하면 요청 목록이 쭉 나옵니다. 목록은 설명을 위한 예시입니다. 실제로는 이미지·폰트까지 수십 줄이 나오니, 필터에서 Fetch/XHR만 고르면 API 요청만 보입니다.
