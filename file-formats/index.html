⚠️ CSV · 쉼표 하나가 칸을 쪼갭니다

단순해 보여서 가장 많이 사고 나는 형식

EQ-03,"PM 완료, 점검 필요",4005.5
EQ-03PM 완료, 점검 필요4005.5
EQ-03,PM 완료, 점검 필요,4005.5
EQ-03PM 완료 점검 필요4005.5 ?

값 안에 쉼표가 있으면 큰따옴표로 감싸야 합니다. pandas의 to_csv는 알아서 합니다 — 손으로 이어 붙이지 마세요.

  • 1앞자리 0 — 엑셀이 007을 7로ID는 글자로
  • 2날짜 자동 변환 — 11-23이 23-Nov으로엑셀 저장 금지
  • 3구분자 — 쉼표 대신 ; · 탭(TSV)sep=
  • 4머리말 줄 — 장비 로그의 헤더 3줄skiprows=3
  • 5소수점 — 큰 수의 4,005.5thousands=","
1 · 2번은 "엑셀로 열었다가 저장"할 때 생깁니다. 원본 CSV는 엑셀로 저장하지 않는 게 규칙입니다. 읽을 때는 dtype={"eq": str}처럼 글자로 읽으라고 지정합니다. 4번은 SQL 덱에서 본 장비 CSV의 헤더 3줄과 같은 이야기입니다.

⚠️ YAML · 읽기 쉬운 대신 눈치를 봅니다

YAML은 값을 알아서 추측합니다 — 가끔 틀리게

country: NO
version: 1.10
lot: 007
on: yes
>>> yaml.safe_load(...)
{'country': False, 'version': 1.1, 'lot': 7, True: True}

노르웨이(NO)는 거짓이 되고, 버전 1.10은 1.1이 됩니다. 글자는 따옴표로 감싸면 끝.

들여쓰기 = 문법

스페이스 두 칸 차이로 다른 뜻이 됩니다. 탭 문자는 금지 — 에디터가 탭을 스페이스로 바꾸게.

목록은 - 로

exclude: 아래 - EQ-01. 대시 뒤 한 칸 띄우기.

읽을 땐 safe_load

파이썬에선 yaml.safe_load. 남이 준 YAML을 그냥 load하면 위험할 수 있습니다.

출력은 PyYAML(safe_load)로 실제로 돌려 본 결과입니다. YAML 1.1 규칙 때문에 yes · no · on · off가 참 · 거짓으로 읽힙니다. K8S 설정, Docker compose, GitHub Actions가 모두 YAML입니다. 다음 덱들에서 계속 만납니다.
ENCODING · 글자는 숫자로 저장된다

"측정값"은 파일 속에서 숫자 몇 개입니다 — 글자표마다 다른

UTF-8 ecb8a1 eca095 eab092 한 글자 = 3바이트 · 전 세계 표준
CP949 c3f8 c1a4 b0aa 한 글자 = 2바이트 · 옛 Windows 한국어 (EUC-KR 확장)

UTF-8로 쓰고 → CP949로 읽으면

측정값 → 痢≪젙媛�

숫자를 엉뚱한 표에서 찾으니 한자 · 이상한 한글이 나옵니다.

CP949로 쓰고 → UTF-8로 읽으면

UnicodeDecodeError: 'utf-8' codec can't decode byte 0xc3 in position 0: invalid continuation byte

UTF-8 규칙에 안 맞는 숫자라 아예 멈춥니다.

같은 색 묶음이 한 글자입니다. 바이트 값과 깨진 결과는 파이썬으로 실제 변환해 본 값입니다. "인코딩"은 글자 ↔ 숫자 변환표의 이름일 뿐입니다. 파일 안에는 숫자만 있고, 어떤 표로 썼는지는 적혀 있지 않은 경우가 많습니다. 그래서 읽는 쪽이 맞혀야 합니다.
FIX · 증상으로 처방 고르기

증상원인처방 (pandas)

utf-8-sig = UTF-8 + 앞머리 표시(BOM)

파일 맨 앞 3바이트 ef bb bf가 "나 UTF-8이야"라고 알려 줍니다. 엑셀이 이걸 보고 한글을 제대로 엽니다.

팀 규칙 한 줄

새 파일은 전부 UTF-8. 엑셀로 열 CSV만 utf-8-sig. 옛 장비 파일은 읽을 때 cp949 → 바로 UTF-8로 저장.

클릭할 때마다 한 줄씩. 사내 실무에서 거의 이 네 가지로 끝납니다. 모르겠으면 AI에게 "이 파일의 앞 200바이트를 16진수로 보여주고 인코딩을 추정해줘"라고 하면 됩니다.

줄바꿈도 글자입니다 — Windows는 두 개, 나머지는 하나

EQ-03,4005.5\r\nCRLF · Windows
EQ-03,4005.5\nLF · macOS · Linux · 서버
$ git add run.sh

대부분은 몰라도 된다

파이썬 · 엑셀 · VS Code는 둘 다 알아서 읽습니다. git 경고도 대개 무시해도 됩니다.

문제가 되는 한 곳 — 서버 스크립트

Windows에서 쓴 .sh를 리눅스 서버 · 컨테이너에서 돌리면 /bin/bash^M: bad interpreter. \r 때문입니다.

VS Code 오른쪽 아래

"CRLF"를 눌러 "LF"로 바꾸면 끝. Docker 덱에서 다시 만납니다.

^M은 \r을 화면에 표시한 모양입니다. Dockerfile이나 리눅스용 스크립트는 LF로 저장하는 습관을 들이면 됩니다.
③ PATHS · 역슬래시의 함정

파이썬 글자 속 \는 "다음 글자가 특별하다"는 뜻

C:\new\test.csv
\n = 줄바꿈\t = 탭
open("C:\new\test.csv")     # ❌ 줄바꿈 · 탭이 섞임
open(r"C:\new\test.csv")    # ✅ r = 있는 그대로
open("C:/new/test.csv")     # ✅ Windows도 / 를 알아들음
# ✅✅ 가장 좋은 방법 — pathlib
from pathlib import Path

HERE = Path(__file__).resolve().parent   # 이 .py 파일의 폴더
raw  = HERE / "data" / "raw.csv"         # / 로 이어 붙임

raw.exists()                 # 있나?
for f in (HERE / "data").glob("*.csv"):  # CSV 전부
    print(f.name)
out = raw.with_suffix(".parquet")        # 확장자만 바꾸기

OS마다 구분 기호를 알아서 맞추고, 실행 위치와 상관없이 같은 파일을 찾습니다.

탐색기에서 복사한 경로를 그대로 붙이면 이 함정에 빠집니다. 문자열 앞에 r을 붙이거나, / 로 바꾸거나, pathlib을 씁니다. Path(__file__) 부분은 터미널 덱의 "상대 경로는 서 있는 곳 기준" 문제를 함께 해결합니다.

AI · 파일 규칙 알려 주기

AI는 인코딩을 기본값으로 가정합니다 — 적어 주세요

# CLAUDE.md — 파일 규칙
- 경로는 pathlib, 스크립트 위치 기준
- 장비 원본 CSV: cp949, 헤더 3줄, eq는 글자(str)
- 새로 만드는 파일: UTF-8
- 엑셀용 CSV 출력: utf-8-sig
- JSON 저장: ensure_ascii=False, indent=2
- 원본 파일은 덮어쓰지 말고 out/ 에 저장
- 파일을 읽으면 head(3) · shape 를 먼저 보여줄 것

왜 적어야 하나

AI는 보통 UTF-8을 가정합니다. 사내 옛 파일(cp949)에서 첫 실행이 항상 실패하는 이유.

샘플을 같이 주기

"이 파일의 첫 5줄" 원문을 붙여 주면 구분자 · 헤더 · 단위를 AI가 직접 봅니다. 민감한 값은 가리고.

원본은 읽기만

SQL 덱의 "읽기 전용" 원칙과 같습니다. 결과는 늘 새 파일로.

일곱 줄짜리 규칙이 이 덱 전체의 요약입니다. 그대로 복사해 프로젝트 CLAUDE.md에 붙이고 팀 사정에 맞게 고치세요.
