PROBLEM · 내 PC 서버의 한계

"링크 좀 보내 줘"에서 문제가 시작됩니다

💤 내 PC가 꺼지면 끝

퇴근하고 PC를 끄면 팀의 대시보드도 꺼집니다. 휴가 중엔 아무도 못 씁니다.

💥 죽으면 아무도 모름

새벽에 에러로 멈춰도 다시 켜 줄 사람이 없습니다. 아침에 "안 돼요"라는 메신저를 받고서야 압니다.

🧩 "내 PC에선 되는데"

다른 서버로 옮기면 파이썬 버전, 패키지, 경로가 달라서 돌아가지 않습니다.

K8S가 해결하는 건 바로 이 세 가지 — 항상 켜져 있게, 죽으면 다시 켜게, 어디서나 똑같이.

바이브 코딩으로 도구를 만들면, 다음 단계는 거의 항상 "팀이 같이 쓰게 해 줘"입니다. 그때 부딪히는 세 가지 문제를 먼저 공감시킵니다. 세 번째(환경 차이)는 컨테이너가, 앞의 두 개(항상 켜짐·자동 재시작)는 K8S가 해결합니다.
THE STAIRS · 꼭 K8S까지 가야 하나

한 계단씩 올라갑니다 — 필요할 때만

LV 1내 PC에서 실행

python app.py — 나 혼자 쓸 때.

→ 혼자 쓰면 여기서 충분
LV 2서버 한 대에서 실행

공용 서버에 띄워 두기. 내 PC를 꺼도 돌지만, 프로그램이 죽으면 손으로 다시 켭니다.

→ 몇 명이 잠깐 쓸 때
LV 3컨테이너로 실행

실행 환경째 상자에 담아서 어느 서버에서나 똑같이. 이 단계가 K8S의 전제입니다.

→ 옮기거나 다시 깔 일이 생길 때
LV 4K8S에서 실행

여러 서버 위에서 개수를 유지하고, 죽으면 자동으로 다시 띄우고, 새 버전을 무중단으로 교체.

→ 팀·부서가 매일 쓸 때, 회사에 클러스터가 있을 때
중요한 메시지: K8S는 목표가 아니라 도구입니다. 나 혼자 쓰는 도구를 K8S에 올리면 배보다 배꼽이 큽니다. 회사에 이미 운영 중인 클러스터와 담당 팀이 있다면 LV4의 문턱이 크게 낮아집니다. 직접 클러스터를 만드는 건 이 덱의 범위가 아닙니다.
CONTAINER · 상자에 담기

이미지는 레시피, 컨테이너는 그 레시피로 만든 요리

Dockerfile — FastAPI 대시보드 예시

FROM python:3.11-slim          # 바탕 환경
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .                        # 내 코드
EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

이미지 (image)

코드 + 파이썬 + 패키지를 굳힌 파일. 한 번 만들면 어디서나 같은 결과.

컨테이너 (container)

이미지를 실행한 것. 같은 이미지로 여러 개를 띄울 수 있습니다.

단골 함정: 127.0.0.1

컨테이너 안에서 localhost에만 열면 밖에서 못 들어옵니다. 0.0.0.0으로 엽니다.

Dockerfile은 "이 프로그램이 돌려면 무엇이 필요한가"를 적은 레시피입니다. 이걸로 이미지를 굽고(build), 이미지를 실행하면 컨테이너. 0.0.0.0 함정은 처음 컨테이너를 만들면 거의 모두 겪습니다 — 로컬에선 되는데 컨테이너에선 접속이 안 되면 제일 먼저 확인. requirements.txt를 먼저 복사하는 이유: 코드만 바뀌었을 때 패키지 설치 단계를 다시 하지 않게(캐시) — 질문 나오면 설명.
CONTAINER · 이미지는 층으로 쌓인다

Dockerfile 한 줄이 층 하나 — 바뀐 층부터만 다시 굽습니다

🐍 바탕 환경 — 파이썬 3.11FROM python:3.11-slim
📋 패키지 목록COPY requirements.txt
📦 패키지 설치 (오래 걸림)RUN pip install …
✏️ 내 코드 (자주 바뀜)COPY . .

코드만 고치면 → 맨 위 층만

아래 세 층은 저장해 둔 것(캐시)을 그대로 씁니다. 다시 굽는 데 몇 초면 됩니다.

순서가 속도를 정합니다

자주 바뀌는 것(내 코드)을 맨 위에 둡니다. 코드를 먼저 복사하면 코드 한 줄만 고쳐도 패키지를 매번 새로 설치합니다.

같은 층은 공유됩니다

바탕 이미지가 같은 앱 열 개는 그 층을 한 번만 내려받습니다.

층이 아래부터 하나씩 쌓이는 애니메이션입니다. 앞 장 Dockerfile에서 requirements.txt를 먼저 복사한 이유가 여기서 풀립니다. AI가 만든 Dockerfile에서 COPY . . 가 pip install 보다 위에 있으면, 빌드가 매번 느려지는 원인입니다 — 검토 포인트로 안내.

선언형 — 결과만 적는다

"이 이미지로 3개." 어떻게 맞출지는 K8S가 압니다. 이 문서가 YAML 파일입니다.

K8S를 이해하는 핵심 한 장입니다. 공정에 빗대면 "목표 두께를 정해 두면 장비가 측정하고 보정하는 피드백 제어"와 비슷합니다(대략적인 비유). 이 선언 문서(YAML)를 git에 두면, 무엇이 어떻게 떠 있어야 하는지가 전부 파일로 남습니다 — 하네스 덱의 "말 대신 파일"과 같은 생각입니다.

Deployment가 "Pod 3개 유지"를 지킵니다 — 하나가 죽으면(빨간색) 새로 띄웁니다. 이 모든 Pod는 Node(서버 한 대) 위에서 실행되고, Node 여러 대를 묶은 것이 클러스터입니다.
노란 점이 요청입니다. Service가 살아 있는 Pod들에 나눠 보내는 모습을 보여 줍니다. 왼쪽에서 오른쪽으로 요청을 따라갑니다. 질문을 던져 봅니다: "Pod가 죽었다가 새로 뜨면 주소가 바뀌는데, 사용자는 어떻게 계속 접속하죠?" → 그래서 Service가 고정 주소 역할을 합니다. Ingress는 사내 도메인 이름을 보고 어느 Service로 보낼지 정합니다. 사내에서는 보통 인프라 팀이 Ingress 설정 규칙을 정해 둡니다.

READ THE YAML · 선언서 한 장 읽기

쓰는 건 AI가 해도, 읽을 줄은 알아야 합니다

apiVersion: apps/v1
kind: Deployment                # 개수 유지 선언서
metadata:
  name: dashboard-api
spec:
  replicas: 3                     # ① 3개 유지
  selector:
    matchLabels: { app: dashboard-api }
  template:                       # 찍어낼 Pod 모양
    metadata:
      labels: { app: dashboard-api }  # ② 이름표
    spec:
      containers:
        - name: api
          image: <사내-레지스트리>/dashboard-api:1.0.0 # ③
          ports: [ { containerPort: 8000 } ]
apiVersion: v1
kind: Service                   # 고정 주소
metadata:
  name: dashboard-api
spec:
  selector: { app: dashboard-api }   # ② 같은 이름표
  ports:
    - port: 80                # 밖에서 부르는 번호
      targetPort: 8000        # Pod 안 번호

세 군데만 보면 됩니다

① 몇 개 띄우나 ② 이름표가 서로 맞나 ③ 어느 이미지를 쓰나. ②가 어긋나면 Service가 Pod를 못 찾습니다.

YAML은 AI가 잘 씁니다. 대신 사람이 확인할 곳을 세 군데로 좁혀 줍니다. 특히 ② 라벨 불일치는 "Pod는 잘 떠 있는데 접속이 안 된다"의 가장 흔한 원인입니다. Service의 selector와 Pod의 labels가 글자까지 같아야 합니다. targetPort는 Dockerfile의 8000과 같아야 합니다 — 앞 장과 연결.
EXAMPLE · 이름표 한 글자의 차이

Pod는 멀쩡한데 접속이 안 될 때, 이름표부터 봅니다

✅ 이름표가 같을 때

Service selectorapp: dashboard-api
Pod labelsapp: dashboard-api
$ kubectl describe service dashboard-api
Endpoints: 10.1.2.7:8000,10.1.3.4:8000,10.1.5.9:8000

❌ 한 글자가 다를 때

Service selectorapp: dashboard-api
Pod labelsapp: dashboard_api
$ kubectl describe service dashboard-api
Endpoints: <none> ← 연결된 Pod 0개

증상

Pod 상태는 전부 Running. 그런데 브라우저에서는 응답이 없습니다.

확인

describe service의 Endpoints가 <none>이면 이름표 문제입니다.

처방

AI에게 "selector와 labels를 나란히 비교해 줘"라고 하면 한 번에 찾습니다.

하이픈(-)과 밑줄(_) 한 글자 차이입니다. 사람 눈으로는 놓치기 쉽고, K8S는 에러를 내지 않습니다 — 그냥 "연결된 Pod가 없음"이 될 뿐입니다. IP 주소는 예시입니다. 클릭하면 증상 → 확인 → 처방 순서로 나옵니다.

→
② 사내 저장소에 올리기docker push <레지스트리>/dashboard-api:1.0.1

새 버전은 한 개씩 교체

새 Pod가 준비되면 옛 Pod를 하나씩 내립니다. 사용자는 끊김을 거의 못 느낍니다.

망가지면 되돌리기

kubectl rollout undo deployment/dashboard-api — 직전 버전으로 돌아갑니다.

태그(1.0.1)는 매번 새 번호로 올립니다. latest 하나만 계속 덮어쓰면 무엇이 떠 있는지, 어디로 되돌릴지 알 수 없습니다. 회사에 CI/CD(자동 배포 파이프라인)가 있다면 ①~③은 커밋하면 자동으로 일어납니다. 그래도 흐름을 알고 있어야 막혔을 때 어디서 멈췄는지 압니다.

계속 3개 이상이 손님을 받습니다

새 Pod가 "준비됨"(readiness)이 되어야 옛 Pod를 내립니다. 그래서 사용자는 끊김을 거의 못 느낍니다.

v2가 준비되지 못하면?

교체가 멈추고 v1이 계속 일합니다. rollout undo로 깔끔하게 되돌립니다.

클릭할 때마다 한 단계씩 진행됩니다. Deployment의 기본 전략(RollingUpdate)을 단순화한 그림입니다 — 실제로 동시에 몇 개를 더 띄우고 몇 개까지 내릴지는 설정(maxSurge, maxUnavailable)으로 정합니다. 두 번째 카드가 핵심: 망가진 새 버전이 전체를 무너뜨리지 않습니다. 단, readinessProbe가 있어야 "준비됨"을 제대로 판단합니다(심화 장).
⚠️ CONFIG · 설정과 비밀은 코드 밖으로

DB 주소와 비밀번호를 이미지에 굽지 않습니다

# ❌ 코드·이미지 안에
DB_PASSWORD = "p@ssw0rd"
# ✅ Deployment 에서 Secret 을 연결
env:
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef: { name: dashboard-db, key: password }

ConfigMap — 바뀌는 설정

DB 주소, 로그 수준처럼 환경마다 다른 값. 이미지는 그대로 두고 값만 바꿉니다.

Secret — 비밀값

기본 상태의 Secret은 암호화가 아니라 base64 인코딩입니다. 누가 읽을 수 있는지는 권한으로 제한해야 합니다.

Secret YAML을 git에 올리거나 AI에게 보여주지 않습니다 — 보안 약속 2.

base64는 누구나 디코딩할 수 있습니다. Secret이 "안전한 금고"인 건 저장 암호화와 접근 권한을 클러스터 쪽에서 설정했을 때입니다 — 사내 정책을 확인. AI에게 YAML을 만들게 할 때도 비밀값은 TODO로 비워 두게 하고, 실제 값은 사람이 사내 절차로 넣습니다.
INTRANET · 사내망이라서 달라지는 것

외부 인터넷이 막혀 있으면, 이 세 가지가 달라집니다

① 이미지는 사내 저장소에서

Docker Hub 같은 외부 저장소에 접속할 수 없습니다. 바탕 이미지(python:3.11-slim)도 사내 레지스트리에 있는 것을 씁니다.

② 패키지는 사내 미러로

이미지를 구울 때 pip·npm이 외부로 못 나갑니다. 사내 미러 주소를 빌드 설정에 넣어야 합니다.

③ 사내 인증서

사내 HTTPS는 사내 CA를 쓰는 경우가 많습니다. 컨테이너 안에도 그 인증서를 넣어야 "인증서 오류"가 사라집니다.

복사해서 쓰는 명령 (읽기만 함)

# 1) 상태 보기
kubectl get pods -n <네임스페이스>

# 2) 이유 보기 — 맨 아래 Events
kubectl describe pod <이름> -n <네임스페이스>

# 3) 프로그램이 남긴 말 — 죽기 직전 것
kubectl logs <이름> -n <네임스페이스> --previous

# 접속 불가면: Endpoints 가 비었나?
kubectl describe service <이름> -n <네임스페이스>
순서가 중요합니다: get으로 상태 이름을 보고 → describe의 Events에서 이유를 보고 → 프로그램 문제면 logs. --previous는 재시작되기 전 컨테이너의 로그입니다. CrashLoopBackOff에서 현재 로그가 비어 있을 때 씁니다. describe service에서 Endpoints가 비어 있으면 Service가 Pod를 못 찾는 것 — 대부분 라벨 불일치입니다. 이 명령들은 모두 읽기 전용이라 AI에게 맡겨도 안전한 편입니다(다음 장).

🙋 ask — "envFrom 두 줄을 추가하고 apply 해도 될까요? 먼저 diff를 보여드릴게요"

(2) AI는 읽기 명령까지는 스스로 했지만, apply는 diff를 보여준 뒤 허락을 받고 했습니다(다음 장의 권한 표). KeyError: 'DB_HOST'처럼 "환경변수가 없다"는 CrashLoopBackOff의 가장 흔한 원인 중 하나입니다 — ConfigMap 장과 연결.

운영 클러스터는 사람이

연습·개발 클러스터에서 AI와 시도하고, 운영 반영은 사람이 확인하고 실행합니다.

하네스 덱의 "③ 권한" 칸을 K8S에 적용한 장입니다. kubeconfig(클러스터 접속 정보)도 비밀이므로 AI가 읽지 않게 deny 대상입니다. 회사 정책상 AI 에이전트가 클러스터에 접근하는 것 자체가 허용되는지 먼저 확인합니다(보안 약속 3).

DEEPER · 오래 잘 돌게 하는 두 줄

"살아 있나"와 "얼마나 먹나"를 적어 두면 K8S가 더 똑똑해집니다

containers:
  - name: api
    readinessProbe:           # 손님 받을 준비 됐나
      httpGet: { path: /health, port: 8000 }
    livenessProbe:            # 아직 살아 있나
      httpGet: { path: /health, port: 8000 }
    resources:
      requests: { cpu: 250m, memory: 256Mi }  # 최소 보장
      limits:   { memory: 512Mi }              # 넘으면 OOMKilled

readiness · liveness

준비 안 된 Pod엔 요청을 안 보내고, 멈춘 Pod는 다시 시작합니다. 앱에 /health 주소 하나만 만들면 됩니다.

requests · limits

너무 크게 잡으면 Pending, 너무 작게 잡으면 OOMKilled. 처음엔 인프라 팀 기본값부터.

핵심 모드에서는 접히는 심화 장입니다. 수치는 예시이며, 실제 값은 앱을 돌려 보며 맞춥니다. FastAPI라면 /health 엔드포인트를 AI에게 한 줄로 추가해 달라고 하면 됩니다.
