① LOGGING · 다섯 단계

레벨은 볼륨 조절기 — 평소엔 INFO, 문제 날 땐 DEBUG까지

DEBUG개발 중 세세한 값 · 중간 계산"쿼리 파라미터: eq=EQ-03, day=11-23"
INFO정상 흐름의 이정표"수집 완료 rows=412"
WARNING이상하지만 계속 감"응답 4.8초 — 평소의 3배"
ERROR이번 작업은 실패"DB 연결 실패 retry=3/3"
CRITICAL프로그램 전체가 위험"디스크 98% — 저장 중단"
level=INFO → 이 선 아래만 기록

레벨을 코드 안에 박지 말고 환경변수(LOG_LEVEL=DEBUG)로 바꾸게 해 두면, 문제 날 때 코드 수정 없이 자세히 봅니다.

가로 선이 필터입니다. INFO로 두면 DEBUG는 버려지고 INFO 이상만 남습니다. 애니메이션처럼 선을 위로 올리면 DEBUG까지 보입니다. WARNING과 ERROR를 구분하는 기준: 이번 일을 끝냈으면 WARNING, 못 끝냈으면 ERROR.

숫자를 함께

몇 행, 몇 초, 몇 번째 재시도. "느려졌다"를 숫자로 증명합니다.

남기면 안 되는 것

비밀번호 · 토큰 · 개인정보 · 데이터 원문 통째. 로그 파일은 생각보다 많은 사람이 봅니다.

빨간 줄의 공통점: 아침에 읽어도 무엇을 해야 할지 모릅니다. 초록 줄은 각각 "무엇이, 어디서, 얼마나"가 있습니다. AI에게 "로그 문장은 키=값 형식으로, 비밀 · 개인정보 금지"를 규칙으로 주면 대부분 지킵니다.
① LOGGING · 파일로, 돌려 쓰며, 예외까지

회전(rotation): 자정마다 오늘 파일 이름을 날짜로 바꾸고 새 파일을 엽니다. 14개를 넘으면 가장 오래된 것부터 지웁니다. except: pass는 AI가 "에러 안 나게 해줘"라고 하면 종종 쓰는 패턴입니다. 에러가 사라지는 게 아니라 숨겨집니다. 와치독이 필요한 이유이기도 합니다. encoding="utf-8" — 한글 로그가 깨지지 않게(파일 형식 덱).

💓 하트비트

앱이 일정 간격(예: 30초)마다 "살아 있어요"를 남깁니다. 일을 한 바퀴 돌 때마다.

⏲️ 타임아웃

와치독은 마지막 신호 이후 시간을 잽니다. 기준(예: 2분)을 넘으면 멈춤으로 판단.

🚨 조치

로그 · 알림 → 멈춘 프로세스를 끝냄 → 슈퍼바이저가 다시 띄움.

"프로세스가 있나"만 보면 못 잡습니다. 무한 대기 · 교착 · 응답 없는 DB를 기다리는 중에도 프로세스는 멀쩡히 살아 있으니까요.

애니메이션: 하트비트가 세 번 오다가 끊기면 타이머 막대가 차오르고, 끝까지 차면 감시견이 짖습니다. 핵심은 "죽음"과 "멈춤"의 차이입니다. 죽음은 슈퍼바이저가 바로 알지만, 멈춤은 와치독이 있어야 압니다. 참고: 파이썬의 watchdog 라이브러리는 이름만 같고 "폴더 안 파일이 바뀌면 알려 주는" 다른 용도입니다. 헷갈리지 마세요.
④ WATCHDOG · 직접 만들기

앱은 파일 시각을 갱신하고, 와치독은 그 시각을 잰다

앱 쪽 — collector.py
from pathlib import Path
HB = Path("run/collector.heartbeat")

while True:
    collect_once()                  # 한 바퀴 일하고
    HB.touch()                      # 💓 "살아 있어요"
    time.sleep(30)

일을 한 뒤에 찍는다

별도 스레드에서 시계처럼 찍으면, 본 작업이 멈춰도 신호는 계속 갑니다. 일 한 바퀴 = 신호 한 번.

감시 쪽 — watchdog.py (1분마다 실행)
import time, logging
from pathlib import Path
HB, LIMIT = Path("run/collector.heartbeat"), 120
log = logging.getLogger("watchdog")

age = time.time() - HB.stat().st_mtime
if age > LIMIT:
    log.error("하트비트 끊김 age=%.0fs", age)
    send_alert(f"수집기 멈춤 {age:.0f}초")
    restart_collector()            # 슈퍼바이저에게 맡기기

웹 앱이면 /health

하트비트 파일 대신 GET /health가 200을 주는지 확인합니다 → API 덱.

가장 단순한 와치독입니다. 파일의 수정 시각(mtime)을 하트비트로 씁니다. 실무 도구들도 원리는 같습니다. restart_collector()는 직접 프로세스를 다시 띄우기보다 슈퍼바이저에게 재시작을 요청하는 쪽이 깔끔합니다. 다음 장. 와치독 자체는 작업 스케줄러(Windows) · cron(Linux)으로 1분마다 실행합니다. 와치독이 죽으면? 그래서 와치독은 최대한 단순하게 둡니다.

⑤ SUPERVISOR · 도구는 환경마다

같은 일, 어디서 돌리느냐에 따라 다른 도구

; /etc/supervisor/conf.d/collector.conf  (Linux · supervisord)
[program:collector]
command=/opt/cmp/.venv/bin/python collector.py
directory=/opt/cmp
autostart=true             ; 서버 켜지면 같이
autorestart=true           ; 죽으면 다시
startsecs=10               ; 10초 버티면 "정상 기동"
startretries=3             ; 기동 실패 3번이면 FATAL
stdout_logfile=/var/log/cmp/collector.out.log
stderr_logfile=/var/log/cmp/collector.err.log
어디서도구한 줄
Linux 서버supervisord왼쪽 설정 · supervisorctl status
Linux 서버systemdRestart=on-failure · RestartSec=5
Docker--restartunless-stopped · on-failure:3
K8SDeployment원하는 개수를 늘 유지
Windows PC서비스 · 작업 스케줄러NSSM 등으로 서비스 등록 (사내 승인)

공통 질문 세 개: 언제 띄우나(부팅 시?) · 죽으면 몇 번 다시 · 출력은 어디에 남나.

supervisord는 리눅스 · 맥용입니다. Windows에서는 서비스로 등록하거나(NSSM 같은 도구), 작업 스케줄러의 "실패 시 다시 시작" 옵션을 씁니다. 사내 PC에서는 설치 승인이 필요할 수 있습니다. Docker 덱에서 만든 컨테이너라면 --restart 옵션 한 줄이 가장 쉬운 슈퍼바이저입니다.

AI · 로그 규칙 알려 주기

AI는 print와 except: pass를 좋아합니다 — 규칙으로 막기

# CLAUDE.md — 로그 · 운영
- print 금지, logging 사용 (logger 이름 = 모듈명)
- 형식: "%(asctime)s %(levelname)s %(name)s:%(lineno)d %(message)s"
- logs/ 에 midnight 회전, 14일 보관, utf-8
- 예외는 log.exception 후 다시 raise. except: pass 금지
- 로그에 비밀번호 · 토큰 · 개인정보 금지
- 긴 작업은 한 바퀴마다 run/*.heartbeat 갱신
- LOG_LEVEL 환경변수로 레벨 조절

로그를 AI에게 읽히기

"logs/app.log에서 첫 ERROR 앞뒤 50줄을 보고 원인 후보 3개와 확인 방법을 줘."

재시작으로 덮지 않기

"자꾸 죽으니 재시작 넣어줘"보다 "로그를 보고 왜 죽는지부터". 재시작은 그다음.

일곱 줄짜리 규칙을 복사해 프로젝트 CLAUDE.md에 붙이면, 이후 AI가 쓰는 코드의 로그가 한 형식으로 통일됩니다.

🖐 실습 · 일부러 멈추고 살아나는지 보기 (25분)

로그 → 와치독 → 재시작을 내 스크립트에

배우는 것 — logging으로 바꾸고, 하트비트로 멈춤을 잡고, 재시작 한도를 두는 법.

💬 에이전트에게 이렇게 말하세요
1) 이 스크립트의 print를 logging으로 바꾸고 logs/에 회전 저장해줘.
2) 한 바퀴마다 run/app.heartbeat를 갱신하게 해줘.
3) watchdog.py: 하트비트가 60초 넘게 멈추면 ERROR 로그 +
   프로세스 재시작. 재시작은 최대 3번, 넘으면 멈추고 알려줘.
4) 테스트용으로, 환경변수 HANG=1이면 일부러 멈추는 줄을 넣어줘.

✅ 완료 기준

  • HANG=1로 켜면 60초 뒤 와치독이 멈춤을 기록한다
  • 재시작 횟수가 로그에 1/3 · 2/3 · 3/3으로 남고, 그 뒤엔 멈춘다
  • 로그만 보고 "몇 시에 무엇이" 일어났는지 말할 수 있다

🧯 막히면

재시작 부분이 복잡하면 먼저 1 · 2만 하고, 와치독은 "알림 로그만 남기기"로 시작하세요. 재시작은 Docker의 --restart로 대신할 수 있습니다.
